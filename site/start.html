開始使用

這是一套方法論，不是安裝包。工具能直接跑，但能不能「幹活」取決於你把它接到自己的內容上。

先跑一次校驗工具

方法論倉庫在 GitHub 上，含規格、模板與一支可執行的校驗工具。 先跑它的自我驗收，確認工具真的會擋——只跑正常情況等於沒驗證。

git clone https://github.com/Gary1020-byte/scene-memory-architecture.git
cd scene-memory-architecture
bash 03-可執行工具/反例驗收.sh        # 應顯示 10 通過，0 失敗
反例驗收的存在是因為：校驗工具必須能證明「該失敗時會失敗」。 只跑正常情況的情況下，一個什麼都不擋的工具也會看起來是好的。

最小可用：先只做這四件

  1. 每個場景一份記憶檔案，第一個小節固定寫 §₀ 交接（身分／進度／下一步／卡點）。
  2. 換會話之前必須先寫 §₀。寫不出「下一步」就代表這輪白幹了。
  3. §₀ 控制在 4 KB 內，超了把歷史搬進 歸檔/。
  4. 只記結論，不記過程（每次寫回 ≤ 10 行 / ≤ 2 KB）。
等你有了 3 個以上場景、而且開始出現「同一個事實兩處不一致」，再來補共享層的五塊板。 不要一開始就蓋全套。

開一個自己的場景

從「場景」頁挑一個接近的範本下載，解壓後就得到一個場景的完整骨架。

# 1. 解壓下載的骨架
unzip knowledge.zip -d ~/my-scenes/

# 2. ★ git init —— 這是場景邊界，沒有它引擎不會載入這個場景的技能
cd ~/my-scenes/知識庫 && git init

# 3. 寫 §₀ 交接（我是誰／幹到哪／下一步／卡在哪）

# 4. 產生身份卡與場景畫像
node <工作台>/工具/場景記憶.mjs stamp --場景 知識庫

# 5. 校驗 —— 全綠才算完成
node <工作台>/工具/場景記憶.mjs check --場景 知識庫
第 2 步是最容易漏的。 沒有 .git/，場景專屬技能全部不會被載入——但場景憲法仍會被鏈式載入， 所以症狀不明顯，看起來只是「這個場景好像變笨了」。

規格在哪

文件內容
README.md入口與總覽
總綱.md一圖看懂它怎麼運轉（六層、記憶放哪、誰能寫、活怎麼派）
00-核心機制/累積、場景、場景記憶、派單與回執、工作流、兩套記憶的分工
01-架構總覽/拓撲總覽與工作流地圖
02-落地實作/目錄與檔案規格、交接與校驗、維護手冊、已知裂縫與待修
03-可執行工具/場景記憶.mjs（init/stamp/交接/check）、反例驗收腳本
04-模板/記憶檔、定位卡、派單格式、示範工作台
05-對照與選型/場景 vs 臨時執行體、帳本 vs wiki、選型判據
方法論倉庫的更新清單.md 記每一筆架構變更。 一份不記變更的方法論，會在半年後變成一份謊言。

什麼適合、什麼不適合

適合
  • 願意自己改設定、能讀 markdown 與一點 shell
  • 習慣用檔案系統思考問題，而不是「跟它說一句就好」
  • 把「排查」當正常流程的人
  • 已經在用多個 AI agent，而且被「它們互相干擾」困擾過
不適合
  • 想要一鍵安裝包的人
  • 不想碰檔案結構的人
  • 指望「AI 自己會搞定一切」的人（AI 能幫你改，但得你先說清你的環境）
